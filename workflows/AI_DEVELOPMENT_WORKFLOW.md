# AI 研发工作流

## 1. 需求进入

- 明确业务目标、用户场景、边界和验收标准。
- 标注是否涉及权限、敏感数据、数据库变更、公共协议变更。
- 高风险需求必须先输出设计方案再编码。

## 2. 上下文分析

AI 编码前必须完成：

1. 阅读 `AGENTS.md`、相关模块 README 和设计文档。
2. 分析已有目录结构、依赖关系、公共组件和基础设施能力。
3. 确认 DDD 分层位置与接口边界。
4. 明确测试方式和回归影响范围。

## 3. 方案输出

复杂任务必须先输出：

- 模块边界。
- 领域模型。
- API 设计。
- 数据访问策略。
- 事务策略。
- 安全策略。
- 测试策略。
- 风险与回滚方案。

## 4. 编码实现

编码必须遵循：

- DDD 分层。
- RESTful API。
- 统一异常和返回结构。
- 参数校验。
- 构造器注入。
- MapStruct 转换。
- JUnit 5、Mockito、Testcontainers 测试策略。

## 5. 自检清单

提交前必须确认：

- 代码无 Demo 化实现。
- 无无关依赖和无关重构。
- 无敏感信息泄露。
- 无 `System.out.println` 和 `printStackTrace`。
- 无循环 SQL、N+1 和 `SELECT *`。
- 事务边界清晰。
- 单元测试覆盖核心逻辑。
- 文档和 Prompt 已同步更新。

## 6. AI Review

AI Review 必须输出：

```markdown
## Review 结论

- 总体结论：通过 | 有条件通过 | 不通过
- 风险摘要：<摘要>

## 问题列表

- 等级：Blocker | Critical | Major | Minor | Suggestion
- 位置：<文件:行号>
- 原因：<问题原因>
- 风险：<风险说明>
- 建议：<修复建议>
```

## 7. 合并与沉淀

合并前必须：

- 提交信息符合 Git 规范。
- 测试命令与结果记录在 PR 中。
- 高风险变更已有人审确认。
- 可复用 Prompt、评测用例和问题模式已沉淀。
